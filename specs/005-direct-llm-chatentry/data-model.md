# Phase 1 Data Model — Direct-LLM Chat Entry Endpoint

**Feature**: `005-direct-llm-chatentry`
**Date**: 2026-05-20

This feature introduces no new database tables and no new Alembic
migration. The four domain tables (`feeds`, `sleeps`, `poops`,
`appointments`) and the existing repository layer (feature 001) are
reused without alteration; soft-delete, idempotency, validation, and
time-zone handling are inherited.

The entities documented here are **request, response, and in-process**
shapes — they live in Pydantic models and Python dataclasses, not in
SQLite.

---

## 1. `ChatEntryRequest` (HTTP request body)

| Field             | Type                                                              | Required | Notes                                                                                                                                                                                                                                       |
| ----------------- | ----------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `message`         | `str`, length 1–`momdiary_session_message_max_bytes` (decoded)    | yes      | The caregiver's current turn. Whitespace-stripped on read.                                                                                                                                                                                  |
| `history`         | `list[ChatHistoryTurn]` (default `[]`)                            | no       | Optional client-supplied history. Ignored if a non-empty server-side session resolves first (research.md §3).                                                                                                                                |
| `correlation_id`  | `str` (UUID-v4 form), default = middleware-assigned               | no       | Echoed in logs and the response. Same convention as `/v1/entries`.                                                                                                                                                                            |

`X-Session-ID` is a request **header** (not a body field) so the contract
matches `/v1/entries`.

### `ChatHistoryTurn`

| Field   | Type                                                                       | Required | Notes                                                  |
| ------- | -------------------------------------------------------------------------- | -------- | ------------------------------------------------------ |
| `role`  | `Literal["caregiver", "assistant"]`                                        | yes      | Same vocabulary as the session store (feature 003).    |
| `text`  | `str`, length 1–`momdiary_session_message_max_bytes`                       | yes      | Plain-text content of the prior turn.                  |
| `outcome` | `Literal["created","updated","deleted","clarification_requested","error"] \| null` | no       | Optional, helps the LLM resolve "delete that".         |
| `entry_type` | `Literal["feed","sleep","poop","appointment"] \| null`                | no       | Same.                                                  |
| `entry_id`   | `int \| null`                                                          | no       | Same.                                                  |

### Validation rules

- `message` MUST be non-empty after strip; HTTP 400 otherwise.
- Encoded `message` size MUST NOT exceed
  `momdiary_session_message_max_bytes` (FR-014); HTTP 400 otherwise.
- `history` is bounded only by the per-message size cap and the prompt
  token budget; trimming is applied during prompt assembly (research.md §3).

## 2. `ToolDescriptor` (in-process; not on the wire)

Built on every request from the live `TOOL_REGISTRY`.

| Field         | Type                  | Notes                                                                                                          |
| ------------- | --------------------- | -------------------------------------------------------------------------------------------------------------- |
| `name`        | `str`                 | Registry key, e.g., `"log_feed"`. Catalog also includes the synthetic `"ask_for_clarification"` entry.          |
| `description` | `str`                 | Human-readable one-liner. Sourced from the central `TOOL_DESCRIPTIONS` map.                                     |
| `parameters`  | `dict[str, Any]`      | JSON Schema generated by `<TOOLArgs>.model_json_schema()`; for `ask_for_clarification`, a hand-written schema. |

The descriptor list is the live tool catalog (FR-009).

---

## 3. `LLMDecision` (in-process; LLM response shape)

Discriminated union with `kind` as the discriminator. Validated against
the JSON Schema sent to the LLM via `response_format`. Any deviation
yields outcome `error` with reason `malformed_llm_output`.

### `LLMDecision.tool_call`

| Field        | Type                              | Notes                                                                                                          |
| ------------ | --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `kind`       | `Literal["tool_call"]`            | Discriminator.                                                                                                 |
| `tool_name`  | `str` constrained to live catalog | MUST be a key of `TOOL_REGISTRY` for the *current* request; unknown names fail validation (FR-005).             |
| `arguments`  | `dict[str, Any]`                  | Validated by re-loading the tool's existing Pydantic argument model. Failure → outcome `error` (`invalid_tool_arguments`). |

### `LLMDecision.clarification`

| Field                  | Type                                                          | Notes                                                                                                              |
| ---------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `kind`                 | `Literal["clarification"]`                                    | Discriminator.                                                                                                     |
| `question`             | `str`, length 1–500                                           | The question shown to the caregiver. Maps onto the response's `agent_message`.                                     |
| `suggested_candidates` | `list[SuggestedCandidate] \| null`                            | Same shape as `/v1/entries`'s `SuggestedCandidate` (entry_type, entry_id, summary). Optional.                       |

### State transitions

`LLMDecision` is a transient, single-turn structure. No persistence.
Lifecycle:

```text
LLM returns JSON ──► Pydantic validation
   ├─► tool_call       ──► tool argument re-validation ──► invoke_tool ──► ChatEntryResponse(created|updated|deleted|error)
   ├─► clarification   ──► ChatEntryResponse(clarification_requested)
   └─► validation fail ──► ChatEntryResponse(error, reason=malformed_llm_output)
```

## 4. `ChatEntryResponse` (HTTP response body)

| Field            | Type                                                                                       | Required | Notes                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------ | :------: | ----------------------------------------------------------------------------------------------------------- |
| `outcome`        | `Literal["created","updated","deleted","clarification_requested","error"]`                 | yes      | Maps 1:1 to the failure-mode taxonomy in research.md §6 and to the five spec outcomes.                       |
| `agent_message`  | `str`                                                                                      | yes      | What the chat surface shows the caregiver. For `clarification_requested`, the LLM's `question`.              |
| `entry_type`     | `Literal["feed","sleep","poop","appointment"] \| null`                                     | conditional | Required for `created`/`updated`/`deleted`, omitted otherwise.                                          |
| `entry_id`       | `int \| null`                                                                              | conditional | Required for `created`/`updated`/`deleted`, omitted otherwise.                                          |
| `selected_tool`  | `str \| null`                                                                              | no       | The tool name the dispatcher invoked; useful for debugging and audit.                                       |
| `error_reason`   | `Literal["malformed_llm_output","unknown_tool","invalid_tool_arguments","tool_execution_failed","llm_unavailable","validation_error"] \| null` | conditional | Required when `outcome == "error"`.            |
| `correlation_id` | `str`                                                                                      | yes      | Echoes the request correlation id (or the middleware-assigned one).                                          |
| `session_id`     | `str`                                                                                      | yes      | The server-issued session id used / created for this request. Echoed in `X-Session-ID` response header.      |

### Validation rules

- `outcome == "clarification_requested"` ⇒ `entry_id` and `entry_type`
  MUST be `null`; `agent_message` MUST be non-empty.
- `outcome == "error"` ⇒ `error_reason` MUST be set; `entry_id` and
  `entry_type` MUST be `null`.
- For write outcomes, `entry_type` matches the tool family
  (`log_feed` → `feed`, `update_sleep` → `sleep`, etc.).

---

## 5. Pre-existing entities (reused, unchanged)

This feature reads / writes through the existing repositories without
schema or invariant change:

- `Feed` (`feeds` table) — via `FeedsRepository`.
- `Sleep` (`sleeps` table) — via `SleepsRepository`.
- `Poop` (`poops` table) — via `PoopsRepository`.
- `Appointment` (`appointments` table) — via `AppointmentsRepository`,
  including `add_appointment_note`.
- `ChatTurn` and `ChatSession` (in-memory, feature 003) — via
  `momdiary.agents.session_store.SessionStore` when `X-Session-ID` is
  supplied.

No new ORM model, no Alembic migration, no schema change.
